# Posts to ignore: Ref

Filtering is silent. Dropped posts are not shown to the reader. This file is the only record, so keep it current.

These are research415's proposed rules, carried over from the Cloudless list and adapted for a developer-tools market. **None have been confirmed by Matt yet.** Ask him in the first working session which to keep.

| # | Rule | Why |
|---|---|---|
| 1 | **Teaching, not struggling.** SDD courses, webinars, conference talks, "here is my workflow" threads. | They have a methodology and an audience. They are not looking for a tool. Exception: a course *audience* with no tool loyalty is a campaign target, which belongs in a bullet, not a lead row. |
| 2 | **Already building their own.** Anyone shipping a competing harness, plan tool or MCP server. | They are a competitor, not a customer. Log them in `research/competitors.md` instead. |
| 3 | **Bare-word noise.** Any hit on `ref` meaning referee, git ref, or an unrelated GitHub project. | Search artefact. See the name problem in `CLIENT.md`. |
| 4 | **Affiliate and launch spam.** Awesome-list bots, "featured on" bots, Product Hunt amplification. | Not people. |
| 5 | **Astroturf.** Templated posts from new accounts. Cloudless's Willow case is the reference pattern. | Log the campaign once in a bullet. Never list the posts as mentions. |
| 6 | **Pure model chatter.** Benchmark posts, model releases, "GLM vs Sol" threads with no workflow pain. | Wrong layer. Ref sells the layer above the model. |
| 7 | **Enterprise-scale orgs.** Fortune 100 platform teams with procurement cycles. | Ref has no finished SOC 2 and no self-hosted build. They cannot close these yet. Revisit when SOC 2 lands. |
